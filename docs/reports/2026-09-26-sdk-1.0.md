# Liberty SDK 1.0: build-out report (2026-09-26)

## Scope

This covers the owner's SDK 1.0 brief and the follow-up plan they approved on 2026-09-25:
1. exact damage hooks with full impact context;
2. a broader Blender/content-compiler pipeline;
3. a WorldQuery/physics API;
4. a reusable hook/detour system;
5. safe per-module hot reload.

Everything below was verified by the autopilot, which launches the installed game and drives it, or by offline tests.
Nothing waits on a manual playtest except what the "Open" section says.

## Regression run (2026-09-26)

The full suite ran on the packaged install. 12 of the 14 scenarios passed; the other two were fixed and passed on re-run:
- **`bullet-events` (flaky):** a random ped spawned right after a teleport. SHDN can return a ped object that doesn't
  exist yet, which `PedService.SpawnRandom` didn't treat as a failure. It now retries until its timeout.
- **`inspector-review` (new):** it ran against the older installed build, so it failed. It passes on the new build.

The first scenario after a cold launch can lose its screenshots: Steam's overlay may not take F12 yet, and the desktop
fallback is black under Vulkan. The autopilot now retries F12 once, then fails the step instead of saving a black image
as a pass.

## How the owner uses it

- **Build and install:** `tools/package-phase2.ps1 -GameDirectory <game> -ScriptHookDotNetReference <asi> -LvsDirectory <lvs>`, then
  `tools/install-phase2.ps1 -GameDirectory <game>`, with the game closed.
- **A new prop:** model it in Blender, then in the Liberty panel set the name, collection and template, then Check → Build.
  Package and install; `spawnprop <name>` (autopilot) spawns it.
- **Mod development:**
  1. Build the mod and copy its DLL to `scripts\LibertyFramework\mods`.
  2. In game, run `lf reload <module>`, or turn on `lf hotreload on` once.
  3. Check `lf inspector` for cost and owned resources.

## Decisions made on the owner's behalf

- **Hook scope:** the damage hook only observes (it calls the original first and never changes damage). Changing damage
  needs its own ADR.
- **Compiler v1:** writes static props by patching a game template drawable (the method proven by the slings). One
  material per LOD, DXT1, the template's texture size. Multi-geometry and from-scratch writers are next on the roadmap.
- **Add-on license:** Blender requires GPL-3.0-or-later for add-ons that use `bpy`. It communicates with the rest only
  through files and a process call, so nothing else changes.
- **Portable test Blender:** installed at `D:\LibertyTools\blender-5.2.2-windows-x64` (checksum verified). The owner's
  own Blender profile was not touched.
- **Hot reload limits:** off by default and development-only. Engine-assembly modules can only be restarted.
- **Game folder:** tests never write into the game folder while it runs. Hot reload is tested through `lf reload`.

## Open

1. **Raycast and line of sight:** they need physics reverse engineering. Rule 4 forbids guessing engine behaviour, so
   there is no API yet.
2. **Episodes:** SDK freeze criterion 4 requires the self-test in TLAD and TBoGT, and those runs haven't happened yet.
   The autopilot can't start an episode yet.
3. **Compiler roadmap:**
   - multiple geometries/materials and real LOD models;
   - texture dictionaries written from scratch (DXT5 alpha, any size);
   - collision bounds and world objects;
   - skinned meshes (WDD), fragments (WFT) and vehicles;
   - animations.
4. **Blender previews:** textured renders of the read-back model, plus automatic screenshot comparison in the autopilot.
5. **Owner playtest items:** from `docs/PROJECT_STATE.md`, the gameplay feel of the new trunk wheel and the exact
   damage events in real fights.
